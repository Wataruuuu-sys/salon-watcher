## 1. 目的と背景

ユーザーは美容系サロンにHPB掲載の営業をかけている。営業先は「HPBに未掲載の新店」。**リストに載る件数が増えるほどアタック数が増え、受注機会が増える**（ユーザーはリスト全件にアタックしている）。

現状ユーザーは以下を手作業でやっている:
- Google Mapで新店を探す
- Instagram / Threads で「エリア」「ジャンル」「オープン」「新店」等のキーワード検索

v3（GAS）はGoogle Mapだけを自動化したもので、問題が3つある:
1. Places APIの無料枠に収めるため主要駅周辺しか網羅できない
2. 既知店を検索段階で除外できず毎日全件取り直している
3. Google Map以外（特にSNS）を見ないので鮮度が悪い。SNSでの開業告知はMap登録より早く、確度も高い

**v4の目的: あらゆる媒体から新店情報を高い鮮度で自動収集し、根拠付きのリードリストとしてユーザーに渡し、手作業の工数を削減しつつリード件数を最大化する。**

## 2. ゴール / 非ゴール / アンチゴール

### ゴール
- Instagram・Threads・Google Mapから新店候補を自動収集する（minimoは調査の上で追加判断）
- HPB掲載済みの店を自動で判定し、営業対象から外す（後述: 消さずに下げる）
- 媒体をまたいで同じ店を1件に統合する
- 一度出した店は二度と「新規」として出さない
- 各リードに「新店と判断できた根拠のURL（投稿・ページ）」を付ける
- 対象エリアを多摩地域全域に広げる
- 媒体ごとのリード件数と月額コストを見えるようにし、オーナー/ユーザーが費用対効果を判断できるようにする（作者判断。ユーザーの「費用対効果が見合えばコストをかける」発言を受けて）

### 非ゴール
- 電話番号やDMリンクなど連絡先の自動取得・掲載（最終判断とアタック経路はユーザー側の社内工程に任せる。ユーザーの意思）
- ユーザーの社内システムとの連携・突き合わせ（セキュリティ上不可。社内システム登録済みかの確認はユーザーが目視で行う）
- 自動での営業アクション（DM送信など）
- 店のスコアリング・優先順位付け（全件アタックなので並べ替えの価値は低い）

### アンチゴール（技術的に動いても失敗とみなすもの）
- **本当の新店を見逃すこと。これが最悪。** 誤検出（新店でないものが混ざる）は許容し、見逃しを減らす側に倒す。判定が曖昧なものは落とさず「確度」ラベル付きで残す
- オーナーの普段使いのSNSアカウントが停止されること（スクレイピングには捨てアカウントのみ使う）
- 根拠なしのリード（ユーザーが新店か判断できない行）

## 3. 制約

- 個人ツール。規約上グレーなスクレイピング手段（Apify等）の利用は許容（オーナー判断済み）
- 現在は無料運用。費用対効果が見合えば有料化も可。Phase 1（Threads公式API＋Google Map）はほぼ無料〜少額（LLM判定・Places詳細取得の超過分・AWS利用料のみ）で始め、Instagram追加時（Phase 2）にスパイク結果を見て予算を決める
- インフラはAWS（オーナーが明るい）。言語・フレームワークは根拠があれば自由
- Web UIは継続（ユーザーはブラウザで見る）。保存先はスプレッドシートである必要はない
- 保守はAI駆動 → 構成は素直で、ローカルで動かしやすく、型があるものを優先

## 4. 対象範囲

### ジャンル（6つ）
ヘア / ネイル / アイ（まつエク・まつげパーマ・眉） / リラクゼーション / エステ / 整体

- v3ではヘアを対象外にしていたが、v4では含める（ユーザー要望）
- ヘアは件数が多くなる見込み。UIでジャンル絞り込みができること

### エリア
「西東京」= **多摩地域26市全域**（オーナー確認済み）。
八王子・立川・武蔵野・三鷹・青梅・府中・昭島・調布・町田・小金井・小平・日野・東村山・国分寺・国立・福生・狛江・東大和・清瀬・東久留米・武蔵村山・多摩・稲城・羽村・あきる野・西東京。
西多摩郡（瑞穂町・日の出町・檜原村・奥多摩町）は含めない（作者判断。営業密度が低い）。

エリア定義はコードではなく設定（DB or 設定ファイル）で持ち、追加・削除できるようにする。

### 「新店」の定義（作者判断）
- オープン予定（告知段階）〜オープン後おおむね3ヶ月以内の店
- 移転・リニューアル・新規開業の個人サロン（自宅サロン含む）も対象。営業上は区別しないが、判定時にラベルとして残す

## 5. 情報源

### 5.1 Instagram（Phase 2。ユーザーの経験上もっとも当たりやすい）
費用（Apify従量課金）と公式API審査の重さから、Phase 1ではThreads＋Google Mapで様子を見て、Instagramは後から追加する（オーナー判断）。
**採用方針（オーナー判断）: 公式APIとスクレイピングの組み合わせ。** 広めのハッシュタグ（#新規オープン 等）は公式APIで無料取得し、地名×ジャンルの細かい検索だけApifyで回数を絞って行う。どちらも独立したソースモジュールとして実装し、片方だけでも動く。

- **手段: Apify の Instagram スクレイパー（公式actor `apify/instagram-scraper` 等）**でキーワード/ハッシュタグ/プロフィール検索
  - 公式Graph APIはキーワード検索不可・ハッシュタグ30種/7日・直近24時間のみ・App Review必須のため主力には不向き
- 狙い: 開業告知投稿、プロフィールに「○月OPEN」等がある新規アカウント
- クエリ設計はビルダーに任せるが、最低限「地名 × ジャンル語 × オープン語（オープン/OPEN/新店/開業/グランドオープン/プレオープン/NEW OPEN）」の組み合わせを網羅し、地名は市名＋主要駅名を使う
- 料金はresult課金（調査時点で$1.5〜2.7/1,000件、無料プランに月$5クレジットという情報あり。**未検証**、ビルダーがApifyの現行料金を確認すること）
- Apifyで使うIGアカウント/Cookieが必要な場合は**捨てアカウント**のみ

### 5.2 Threads（第2の柱）
- **手段: 公式 Threads API の `/keyword_search`**（`search_type=RECENT`）
  - 上限: 1ユーザーあたりローリング24時間で2,200クエリ（結果0件はカウントされない）。Meta公式ドキュメント 2026-01-21更新版
  - 他人の公開投稿を検索するには `threads_keyword_search` 権限のApp Review承認が必要。未承認だと自分の投稿しか検索できない
- **スクレイピングは使わない。公式APIのみ**（オーナー判断。検索の確度が高いため）。審査通過まではThreadsソースは無効のまま、Google Mapだけで稼働する。審査待ちの間も、自分の投稿で検索できる範囲で実装・動作確認を進める

### 5.3 Google Map（取りこぼし補完）
- **Places API (New) の Text Search（IDs Only）は無料枠が無制限**（Google公式料金ページで確認、2026-10時点）。v3の制約1・2はコスト問題ではなくなる
- 方針: 多摩地域全域を十分小さいセルに分割し、6ジャンル × 距離順（`rankPreference: DISTANCE`）× `includeFutureOpeningBusinesses: true` で毎日スイープ。セル飽和（60件到達）を検知したら自動で4分割して再検索する（作者判断。v3は手動分割だった）
- 詳細取得は**新規IDのみ**。課金SKUに注意:
  - `formattedAddress` `location` `types` = Essentials
  - `displayName` `googleMapsUri` `businessStatus` `openingDate` = Pro（無料枠 5,000/月）
  - `websiteUri` `userRatingCount` = Enterprise（無料枠 1,000/月）
  - 初回シード時の既存店は詳細不要（IDだけ記録）。新規IDだけPro相当で取り、Enterprise項目（口コミ数・サイトURL）は必要性を見て判断（ビルダー判断。口コミ0件は新店の強いサインなので取る価値はある）
- v3の `known_places`（既知place_id）は移行時に取り込んでベースラインにする
- v3の `new_stores`（通知済みログ）は取り込まない（オーナー判断。v3並行稼働中の重複通知は許容）

### 5.4 minimo（調査項目）
ユーザーが手作業で見ている媒体の1つとして名前が挙がった。新規掲載サロン/新規掲載者を取得できるかは未調査。**Phase 3で調査し、取れるなら追加**。

### 5.5 将来の追加候補（作者判断、今回はスコープ外）
X（旧Twitter）、TikTok、地域情報サイト（号外NET等）、Google検索の新着。ソースはプラグイン的に追加できる構造にしておく。

## 6. 処理の流れ

```
[収集] 各ソース → 生データ（投稿/プレイス）を保存
   ↓
[判定・抽出] SNS投稿はLLMで「対象エリア×対象ジャンルの新店告知か」を判定し、
             店名・ジャンル・市区・開業日・IGアカウント等を抽出
   ↓
[名寄せ] 既存の店舗レコードと照合（店名の正規化・IGアカウント・place_id・住所）
         一致 → 既存店に根拠URLを追加 / 不一致 → 新規店舗
   ↓
[HPB判定] 新規店舗について HPB サイトを店名（＋市区）で検索し掲載有無を判定
   ↓
[通知・表示] 新規リードをメール通知、Web UIに表示
```

### 6.1 LLMによる判定（SNS）
- モデル: Claude Haiku系（最新世代。安価で十分）。ビルダーは実装時に `claude-api` スキルで最新モデルIDと料金を確認すること
- 出力: `is_new_store_announcement`（yes/maybe/no）、店名、ジャンル、市区、開業日（分かれば）、根拠の要約
- **見逃し優先**: `maybe` も残す。`no` だけ落とす。落とした投稿も一定期間は保存し、後から閾値調整できるようにする（作者判断）
- エリア判定は投稿本文・プロフィール・位置情報タグから。エリアが不明な投稿は `maybe` 扱い。ただし対象エリア外と明確に分かるもの（他県の地名等）は `no`
- **`yes` と `maybe` は別枠で表示する**（作者判断）。UIのデフォルトは `yes`＋Map由来、`maybe` は別タブ。メール本文は `yes` を列挙し、`maybe` は件数とUIリンクのみ。ユーザーが `maybe` を対応済み/対象外にした結果は判定プロンプト改善の材料にする

### 6.2 名寄せ
- 同一店判定のキー: Google place_id、Instagramアカウント、正規化した店名＋市区
- 正規化: 全角半角・大文字小文字・記号・「サロン」「salon」等の接尾語の揺れを吸収
- 曖昧一致（類似度）で候補を出し、確信度が低ければ別店舗として扱う（見逃し優先。重複が少し出ても許容）

### 6.3 HPB掲載判定
- HPBの公開検索ページ（beauty.hotpepper.jp）を店名で検索してスクレイピング。v3はGoogle Custom Search APIで判定していたが、同APIが新規受付終了のため廃止済み
- 結果: `掲載あり` / `未掲載` / `判定不能`
- **掲載ありでも行は消さない**。印を付けて一覧の下に回す、またはデフォルトフィルタで隠す（判定ミスにユーザーが気づけるように。作者判断）
- 掲載判定は一度で終わりではなく、未掲載の店は一定期間（例: 1ヶ月）定期的に再判定する（作者判断。営業中に掲載される場合があるため）

### 6.4 実行頻度（作者判断）
- SNS: 1日数回（例: 6時間ごと）。鮮度が価値なので
- Google Map: 1日1回
- メール通知: 1日1回、朝にまとめて（新規0件の日は送らない）

## 7. 出力（ユーザーが見るもの）

### リード1行の項目
- 店名
- ジャンル
- エリア（市区）
- 見つけた媒体（複数可）
- **根拠URL**（開業告知投稿、Map「近日オープン」等。複数媒体で見つかれば全部並べる）
- 確度（LLM判定 yes/maybe、Map由来なら FUTURE_OPENING / 口コミ0件 等のサイン）
- 開業日（分かれば）
- HPB掲載状況
- 初回検出日時

連絡先（電話番号等）は載せない（非ゴール参照）。

### Web UI
- 新着リード一覧（期間・ジャンル・エリア・媒体・HPB状況で絞り込み）
- ユーザーが行ごとに「対応済み / 対象外」を付けられる（作者判断。全件アタック運用で進捗管理に役立ち、誤検出のフィードバックにもなる）
- 運用画面（オーナー向け）: ソース別の件数推移、直近実行の成否、月額コスト概算、Mapセルの飽和状況（v3のスイープログ相当）
- ログイン必須（ユーザーとオーナーのみ）

### 通知
- メール（v3を継承）。件名に件数、本文に店名・ジャンル・エリア・根拠URL・UIへのリンク

## 8. 技術構成（作者判断・根拠付き）

| 役割 | 選定 | 根拠 |
|---|---|---|
| 言語 | TypeScript（全体） | 収集・UIを1言語に統一。型でAI駆動保守のミスを減らす |
| スケジュール | EventBridge Scheduler | cronで複数頻度を素直に表現 |
| オーケストレーション | Step Functions + Lambda | ソースごとに独立実行・リトライ・並列化。GASの6分制限から解放 |
| DB | PostgreSQL（第一候補: Neon無料枠 / 全AWSに寄せるなら Aurora Serverless v2 の0 ACU自動停止） | 名寄せ（`pg_trgm` 類似度検索）と絞り込みがSQLで書きやすい。データ量は数万〜数十万行で小さい |
| Instagram取得 | Apify（APIをLambdaから呼ぶ） | キーワード/プロフィール検索が可能。従量課金 |
| 投稿判定 | Claude API（Haiku系） | 雑多な投稿の判定・抽出精度がリスト品質を決める |
| Web UI | Next.js（静的書き出し）＋API（Lambda）、S3 + CloudFront | オーナーがAWSに明るい |
| 認証 | Cognito（ユーザー2名程度） | AWS内で完結 |
| 通知 | SES | AWS内で完結 |
| IaC | AWS CDK（TypeScript） | 言語統一、再現性 |
| シークレット | Secrets Manager or SSM Parameter Store | APIキー（Places / Apify / Threads / Anthropic）管理 |

DB製品（Neon or Aurora）、UIのホスティング詳細、ORMの選択はビルダーに任せる。

## 9. 段階的リリース（作者判断）

クリティカルパスはSNS対応とHPB掲載判定（オーナー発言）。

オーナー判断: **まず Threads と Google Map で様子を見る。Instagram は後から足せる疎結合な設計にしておく。**

- **ソースはプラグイン構造**: 各ソース（Threads公式API / Google Map / IG公式API / IGスクレイパー / minimo …）は「収集して共通形式の生データを返す」独立モジュール。後段（判定・名寄せ・HPB判定・通知）はソースを知らない。ソースの追加・停止は設定で切り替え、1ソースの失敗が他に波及しない
- **Phase 1**: 基盤（DB・スケジューラ・CDK）＋ ソースのプラグイン枠 ＋ Google Map（v3ロジック移植・全域セル化・自動分割・v3 `known_places` 取り込み）＋ Threads ＋ LLM判定 ＋ 名寄せ ＋ HPB判定 ＋ 最小のWeb UI一覧 ＋ メール通知
  - Threads は公式APIのみ（オーナー判断）。`threads_keyword_search` の審査は Phase 1 着手と同時に申請する（審査待ちが最長の待ち時間になりうるため）
- **Phase 2**: Instagram（公式APIのハッシュタグ検索で広めのタグを無料取得 ＋ Apifyで地名×ジャンルの細かい検索を絞って実行、の組み合わせ）。冒頭でスパイクを行い、費用対効果を見て頻度・クエリ量を決める。スパイクでは**自前スクレイパー（捨てアカウント＋住宅系プロキシ＋ヘッドレスブラウザ）とApifyを比較**し、費用・保守負担・取得率で採用を決める（オーナーの「自前でできないか」を受けて。作者判断）
- **Phase 3**: 運用画面（コスト・件数推移）、対応済みフラグ、再判定ジョブ、minimo調査

v3（GAS）は Phase 1 の Google Map 移行が安定するまで並行稼働させる。

## 10. リスク・未検証事項

| 項目 | 内容 | 対応 |
|---|---|---|
| Apify Instagramの実効性 | 日本語キーワード×地名でどれだけ新店告知が拾えるか未検証。Apifyの多くのactorは自由文の投稿検索ではなくハッシュタグ/プロフィール/場所検索。IG側の仕様変更で壊れる可能性 | Phase 2冒頭に**スパイク**（使い捨て検証）を行う。測るもの: 手段（キーワード・ハッシュタグ・プロフィール検索・場所検索）ごとの「対象エリアの新店告知件数 / 費用」。合格の目安: ユーザーが直近1ヶ月に手作業で見つけた新店（サンプルをもらう）の過半を拾えること（作者判断）。不合格時: ハッシュタグ＋プロフィール検索中心に切り替え、それでも駄目ならInstagramは公式APIのハッシュタグのみで運用する（作者判断）。複数actorを差し替えられる作りにする |
